PROJECT: SYSTEMS LAB
An Interactive Systems Engineering, Simulation & Learning Platform
Build a production-quality, full-stack platform called Systems Lab.

The platform should contain 10 advanced systems-programming projects, implemented using C++, Rust, or both depending on technical suitability.

The primary objective is to make complex systems engineering concepts easy to explore, understand, execute, visualize, experiment with, and deploy.

This is NOT a collection of static educational articles, frontend simulations, or basic coding demos.

Every project must have:

A real working implementation.
A beautiful interactive learning interface.
Detailed architecture diagrams.
Live execution and experimentation.
Internal system observability.
Configurable parameters.
Benchmarks and performance metrics.
Failure injection and recovery experiments where relevant.
Deployment-ready infrastructure.
The platform should make learning advanced C++, Rust, operating systems, networking, databases, concurrency and distributed systems accessible through direct experimentation.

Protocol Buffers where structured service communication is useful.

Deployment architecture:

Frontend: Vercel.
Application API/control plane: separately deployed backend.
Systems execution workloads: isolated Linux containers or dedicated compute instances.
Persistent storage: appropriate database and object storage.
Real-time updates: WebSockets or SSE.

The execution manager should:

Allocate an isolated environment.
Start the appropriate system.
Stream execution events.
Collect metrics.

11. IMPORTANT DEVELOPMENT RULES
Do not sacrifice implementation quality to finish faster.
Do not generate all project code in one pass.
Never build visualizations that misrepresent actual execution.
Explain complex implementation decisions in documentation.
Prefer real execution over simulated results.
Keep every system independently runnable.
Make the learning interface intuitive enough for someone unfamiliar with the underlying implementation.
Make advanced implementation details accessible without overwhelming the learner.
Avoid unnecessary abstractions and overengineering.
Never claim a feature is implemented until it works and has been tested.
Maintain a DEVELOPMENT_STATUS.md containing:

Completed components.
Pending components.
Known bugs.
Test results.
Deployment status.
Current implementation phase.
Next actionable tasks.
At the end of each development phase, provide a concise engineering report.


12. DEFINITION OF DONE
The project is complete only when:

All ten systems have real implementations.
Each system builds and runs independently.
Each system has a detailed architecture.
Every project has an interactive learning interface.
Every playground interacts with its real implementation.
Guided experiments work.
Metrics come from actual execution.
Tests pass.
Documentation is complete.
The frontend is deployed on Vercel.
The backend and execution infrastructure are deployed separately.
Users can access and experiment with the systems through the public website.
Final vision:

A user visits Systems Lab, selects Distributed Database, understands its architecture, explores the source code, starts a five-node cluster, writes data, kills the leader, watches Raft elect a new leader, observes replication, examines the logs and benchmarks the system.

The same experience should exist across all ten systems.

Build this as a cohesive, genuinely functional systems engineering learning platform — not ten disconnected tutorials.

Start by inspecting the repository, proposing the complete architecture and implementation roadmap, and then build Phase 1. Do not begin all ten systems simultaneously.

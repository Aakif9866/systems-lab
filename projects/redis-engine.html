~/overview

What it is, simply

An in-memory database you talk to over the network with short text commands like SET, GET and ZADD.

Keeping data in RAM and processing commands one at a time on a single thread is fast and simple — no locks needed.

  • ›Redis, Valkey, KeyDB, Dragonfly
  • ›Caching layers, session stores, rate limiters, leaderboards, job queues

alternatives

  • ›Memcached (simpler, multi-threaded)
  • ›Multi-threaded shared-nothing designs (Dragonfly)

~/internals

Learn the internals

01 Why single-threaded is fast

No two commands ever run at once, so nothing needs a lock.

The loop only does work when sockets are ready (epoll), each command is O(1) or O(log n) on in-memory structures, and network I/O dominates. MULTI/EXEC is atomic for free.

common mistake · Running O(n) commands like KEYS * in production — they block every client.

02 RESP

A tiny text protocol: '*2\r\n$3\r\nGET\r\n$1\r\nk\r\n'.

Arrays of bulk strings with explicit byte lengths, so parsing never scans for delimiters inside values and binary data is safe.

common mistake · Using character length instead of byte length — breaks on UTF-8 (the tests cover it).

03 Skiplist with spans

A sorted linked list with express lanes; each lane remembers how many nodes it skips.

Random levels (p=0.25) give O(log n) search; summing spans along the search path gives a node's rank, which makes ZRANK and ZRANGE by index fast.

common mistake · Forgetting to update spans of levels above the inserted node's height.

04 Two kinds of expiry

Delete expired keys when someone touches them, and also sweep a few at random.

Lazy expiry alone leaks keys nobody reads; active expiry samples volatile keys and repeats when many were expired, bounding memory waste and CPU.

common mistake · Scanning every key with a TTL each tick — O(n) and blocks the loop.

~/build

How the C++ version gets built

  1. 01Networking — Non-blocking sockets + epoll edge-triggered loop; per-client read/write buffers.
  2. 02Protocol — Incremental RESP parser with zero-copy string views.
  3. 03Data structures — Incrementally-rehashed hash table, skiplist + dict zsets, quicklist-style lists.
  4. 04Durability — AOF with fsync policies and background RDB snapshots via fork().
  5. 05Replication — PSYNC-style replica stream with a backlog buffer.

~/overview

What it is, simply

A database that stores keys and values on several machines at once, so it keeps working when one of them dies.

One machine eventually fails. Copying data to several machines only helps if they agree on the order of writes — that agreement is consensus.

LSM treesWALSSTablesBloom filtersCompactionRaftLeader electionReplication

used in the real world

  • ›etcd and Consul (Raft) behind Kubernetes and service discovery
  • ›CockroachDB, TiKV, YugabyteDB (Raft + LSM)
  • ›RocksDB / LevelDB (LSM) inside countless systems
  • ›Cassandra and ScyllaDB (LSM, leaderless)

alternatives

  • ›B-tree engines (InnoDB, Postgres heap + btree) — faster reads, slower writes
  • ›Paxos / Multi-Paxos, Viewstamped Replication
  • ›Leaderless quorum replication (Dynamo-style)

limitations

  • !Writes need a majority: 5 nodes survive 2 failures, not 3
  • !Every write goes through one leader
  • !LSM trades write speed for read and space amplification

~/internals

Learn the internals

01 Write-ahead log

Write it in the diary before you do it, so you can redo it after a crash.

Each mutation is appended to the WAL, then applied to the memtable. On restart the WAL is replayed into a fresh memtable. Once the memtable is flushed to an SSTable the WAL can be truncated (a checkpoint).

common mistake · Applying to memory first and logging second: a crash between the two loses an acknowledged write.

02 LSM tree

Collect writes in memory, dump them to disk in sorted batches, tidy up in the background.

Writes are sequential (fast). Reads check the memtable, then L0 newest→oldest, then L1. Compaction merges tables, keeps the newest version of each key and drops tombstones at the bottom level.

common mistake · Forgetting tombstones: a delete must shadow older values in lower levels until compaction removes both.

03 Bloom filters

A tiny 'definitely not here / maybe here' test that saves a disk read.

k hash functions set k bits per key. Lookups check those bits; any zero means absent. False positives are possible, false negatives never. ~10 bits/key gives ~1% false positives.

common mistake · Using signed hash arithmetic — negative bit positions silently break the filter (we hit this bug; the tests caught it).

04 Leader election

If nobody hears from the boss for a while, someone volunteers and asks for votes.

Followers start an election after a randomized timeout. A candidate increments its term and requests votes; a node votes once per term and only for candidates whose log is at least as up to date. Majority ⇒ leader.

common mistake · Fixed timeouts: everyone times out together and votes split forever. Randomization breaks the tie.

05 Commit rule

A write counts once most nodes have it — and only entries from the leader's own term are counted directly.

The leader advances commitIndex to N if a majority has matchIndex ≥ N and log[N].term == currentTerm. Earlier-term entries commit indirectly. A new leader appends a no-op so this happens promptly.

common mistake · Committing an old-term entry by counting replicas: Figure 8 of the Raft paper shows how that loses data.

~/experiments

Guided experiments

Run these in the playground above. Write down what you expect before you start.

  1. E1 Kill the leader

    objective ·
    Watch Raft recover from leader failure without losing committed writes.
    do ·
    Start the cluster, write 20 keys, kill the leader, keep writing.
    expect ·
    Writes fail for ~10–20 ticks (election timeout), a new leader appears with a higher term, all committed keys are still readable.

  2. E2 Split brain that isn't

    objective ·
    Show why a minority partition can't accept writes.
    do ·
    Partition {leader, 1 follower} | {3 followers}. Write to the old leader. Heal.
    expect ·
    The majority elects a new leader. The old leader's write never commits and is truncated on heal.

  3. E3 Compaction and amplification

    objective ·
    Measure write amplification of an LSM tree.
    do ·
    Run a write-heavy workload on few keys; watch flushes and compactions.
    expect ·
    Write amplification climbs above 1 because the same keys are rewritten by every compaction.

  4. E4 Crash and replay

    objective ·
    See the WAL save unflushed data.
    do ·
    Kill a follower mid-workload, restart it.
    expect ·
    wal_replay event; the node catches up from the leader and its store matches the others.

~/build

How the Rust version gets built

  1. 01Storage engine — memtable (BTreeMap) → WAL with fsync + CRC framing → SSTable writer/reader with block index and bloom filter.
  2. 02Compaction — Leveled compaction on a background Tokio task; manifest file tracks live tables atomically.
  3. 03Raft core — Pure state machine (no I/O) driven by messages + ticks, so it can be tested deterministically like this mini version.
  4. 04Transport — gRPC (tonic) between nodes; persistent term/vote/log via the WAL.
  5. 05Fault injection — A proxy layer in the execution harness drops/delays packets and kills containers on command.
  6. 06Observability — Events in the standard envelope (leader_changed, append_entries, flush, compaction) + Prometheus metrics.

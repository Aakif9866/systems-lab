~/overview

What it is, simply

The engine underneath async code: it runs many tasks on a few threads by switching between them whenever one is waiting.

A thread per connection wastes memory and time sleeping. An async runtime lets one thread serve thousands of waiting connections.

Futures & pollWakersExecutorsWork stealingReactorTimersBackpressureCancellation

used in the real world

  • ›Tokio (most async Rust: Axum, tonic, Hyper)
  • ›Go's scheduler (goroutines)
  • ›Java virtual threads, .NET thread pool
  • ›Node.js event loop (single-threaded variant)

alternatives

  • ›Thread per request (simple, heavy)
  • ›Callbacks / event loop only (Node)
  • ›Green threads with stacks (Go)

limitations

  • !CPU-bound work gets no speedup from async
  • !A task that blocks the thread stalls everything on that worker
  • !Harder debugging; Pin and lifetimes in Rust

~/internals

Learn the internals

01 poll and Pending

Ask a task 'are you done?'; if it's waiting, it leaves a phone number and goes to sleep.

Future::poll(cx) returns Ready(v) or Pending. Before returning Pending a future must arrange for cx.waker().wake() to be called when progress is possible — otherwise it sleeps forever.

common mistake · Returning Pending without registering a waker: the task hangs silently.

02 Work stealing

Idle workers take half the queue of a busy one.

Local queues avoid contention; stealing half (from the back) balances load in few operations. Tokio also uses a LIFO slot for the most recently woken task for cache locality.

common mistake · One global locked queue: fine at 2 threads, a bottleneck at 32.

03 Pin, Send, Sync

Rules that let Rust prove async code is memory-safe across threads.

Async fns compile to self-referential state machines, so they must not move once polled (Pin). Send lets a task move between worker threads; Sync lets references be shared. Holding a non-Send value (Rc, MutexGuard) across .await makes the future !Send.

common mistake · Holding a std::sync::MutexGuard across .await — blocks the worker and makes the future !Send.

04 Backpressure

When the consumer is slow, make the producer wait instead of buffering forever.

A bounded channel parks senders when full. Memory stays bounded and the slowest stage sets the pace.

common mistake · Unbounded channels: memory grows until the process dies under load.

~/experiments

Guided experiments

Run these in the playground above. Write down what you expect before you start.

  1. E1 Async vs sync

    objective ·
    Why async wins on I/O-bound work.
    do ·
    Run io-heavy in async mode, then sync (thread-per-task) mode with the same workers.
    expect ·
    Async finishes several times faster; on cpu-heavy both are equal.

  2. E2 Work stealing

    objective ·
    Balance an imbalanced queue.
    do ·
    Run imbalanced with stealing on and off.
    expect ·
    Without stealing one worker does everything; with stealing the makespan drops ~4×.

  3. E3 Backpressure

    objective ·
    See a full channel park the producer.
    do ·
    Run pipeline and watch the producer's wakes and the channel's max depth.
    expect ·
    Channel never exceeds capacity 4; producer repeatedly parked and woken.

  4. E4 Deadlock

    objective ·
    Blocking threads can deadlock where async can't.
    do ·
    Run pipeline in sync mode with 1 worker.
    expect ·
    Deadlock detected; async mode with 1 worker completes.

~/build

How the Rust version gets built

  1. 01Task + waker — Arc<Task> implementing ArcWake/RawWaker vtable; state machine with atomic flags.
  2. 02Executor — Worker threads with crossbeam-deque local queues and a global injector.
  3. 03Reactor — mio/epoll registration + hierarchical timer wheel.
  4. 04Primitives — Bounded mpsc channel, JoinHandle with cancellation on drop, timeouts.
  5. 05Instrumentation — Poll/wake events streamed to the visualizer, like tokio-console.

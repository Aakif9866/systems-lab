~/overview

What it is, simply

A tool that remembers every version of your files, lets you work on parallel branches, and combines them again.

Collaboration needs history, safe experimentation and a reliable way to merge everyone's work.

Content addressingSHA-1Blobs, trees, commitsStaging indexBranchesMyers diffThree-way merge

used in the real world

  • ›Git (Linux, nearly all software)
  • ›Mercurial, Fossil, Jujutsu
  • ›Content addressing also powers IPFS, Nix, Docker image layers

alternatives

  • ›Centralized VCS (Subversion, Perforce)
  • ›Patch-based VCS (Darcs, Pijul)

limitations

  • !SHA-1 is collision-weak (git is moving to SHA-256)
  • !No delta compression/packfiles in the mini version
  • !Rename detection not implemented

~/internals

Learn the internals

01 Content addressing

Name every file version by a fingerprint of its contents.

hash = SHA-1('blob ' + byteLength + '\0' + content). Same content ⇒ same name ⇒ stored once, and any corruption changes the name.

common mistake · Hashing just the content — git's header is part of the hash (the tests check git's exact value for 'hello').

02 Snapshots, not diffs

Each commit is a full picture of the project; unchanged files are shared.

A commit points to a root tree; unchanged subtrees keep their hashes, so a new commit only writes the objects that changed.

common mistake · Thinking git stores diffs per commit — diffs are computed on demand (packfiles add deltas later, as compression).

03 Myers diff

Find the fewest insertions and deletions that turn A into B.

Greedy search over edit distance D on diagonals k = x − y, following 'snakes' of equal lines; backtracking the trace yields the edit script. O(ND).

common mistake · Line-by-line comparison without alignment — one inserted line marks everything after it as changed.

04 Three-way merge

Compare both branches to their common ancestor; take each side's changes; conflict only where both changed the same lines.

Find the merge base (lowest common ancestor), diff base→ours and base→theirs into hunks, apply non-overlapping hunks, emit <<<<<<< ======= >>>>>>> where they overlap differently.

common mistake · Two-way merges: without the base you can't tell who changed what.

~/experiments

Guided experiments

Run these in the playground above. Write down what you expect before you start.

  1. E1 Deduplication

    objective ·
    Same content, one object.
    do ·
    Write two files with identical content, add, commit.
    expect ·
    Object store shows 1 blob for 2 files.

  2. E2 Clean merge

    objective ·
    Non-overlapping edits merge automatically.
    do ·
    Branch, edit line 1 on main and line 5 on the branch, merge.
    expect ·
    A merge commit with two parents and both edits.

  3. E3 Conflict

    objective ·
    Overlapping edits need a human.
    do ·
    Edit the same line on both branches, merge.
    expect ·
    Conflict markers; commit refused until resolved.

  4. E4 Fast-forward

    objective ·
    When no merge commit is needed.
    do ·
    Branch, commit on the branch only, merge into main.
    expect ·
    main simply moves to the branch's commit.

~/build

How the C++ version gets built

  1. 01Object store — zlib-compressed loose objects under .lab/objects/ab/cdef…, SHA-1 via OpenSSL (SHA-256 option).
  2. 02Index — Binary index file with stat data for fast status.
  3. 03History — Commit graph walking, merge-base, log --graph rendering.
  4. 04Diff/merge — Myers + patience diff, diff3 merge, conflict resolution workflow.
  5. 05Packing — Delta compression against similar objects and packfiles with an index.

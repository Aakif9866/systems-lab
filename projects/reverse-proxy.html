~/overview

What it is, simply

A server that sits in front of your app servers, forwards each request to one of them, and routes around the broken ones.

One backend can't handle all traffic and will sometimes fail. A proxy spreads load and hides failures from users.

Load balancingConsistent hashingHealth checksCircuit breakersRetriesRate limitingConnection pooling

used in the real world

  • ›NGINX, HAProxy, Envoy, Traefik
  • ›Cloudflare Pingora (Rust), AWS ALB/ELB
  • ›Service meshes (Istio/Linkerd sidecars)

alternatives

  • ›DNS round-robin (no health awareness)
  • ›Client-side load balancing (gRPC)
  • ›L4 (TCP) balancers like IPVS

limitations

  • !Retries can amplify load during an outage (retry storms)
  • !Consistent hashing remaps keys when nodes change
  • !The proxy itself must be redundant

~/internals

Learn the internals

01 Least connections

Send the next request to whoever is least busy right now.

Fast backends finish sooner, so they have fewer active connections and receive more traffic — load adapts to speed automatically.

common mistake · Round-robin with mixed-speed backends: the slow one builds a queue.

02 Consistent hashing

Put servers on a clock face; each key goes to the next server clockwise.

Removing a server only remaps the keys it owned (~1/N). Virtual nodes (many points per server) smooth the distribution.

common mistake · hash(key) % N — changing N remaps almost every key.

03 Circuit breakers

Stop calling a service that keeps failing, check back later.

Failing fast protects the caller's threads and gives the backend room to recover. Half-open admits a single trial so recovery is detected without a stampede.

common mistake · Retrying into an open circuit — or retries without a budget, creating a retry storm.

04 Token bucket

Requests spend tokens; tokens drip back at a fixed rate.

Allows bursts up to the bucket capacity while capping the long-run rate.

common mistake · Fixed one-second windows: bursts at the boundary double the allowed rate.

~/experiments

Guided experiments

Run these in the playground above. Write down what you expect before you start.

  1. E1 Kill a backend

    objective ·
    Health checks + retries hide failures.
    do ·
    Kill one backend with retries 0, then 2.
    expect ·
    Errors until health checks eject it; with retries clients barely notice.

  2. E2 Trip the breaker

    objective ·
    Watch closed → open → half-open → closed.
    do ·
    Set a backend's error rate to 100%, then back to 0.
    expect ·
    breaker_open, no traffic, half-open trial, breaker_closed.

  3. E3 Strategies under skew

    objective ·
    RR vs least-conn with a slow backend.
    do ·
    Make one backend 10× slower; switch strategies.
    expect ·
    Least-conn shifts traffic away from it; p99 drops.

  4. E4 Rate limiting

    objective ·
    Cap throughput.
    do ·
    Push RPS above the refill rate.
    expect ·
    429s appear; admitted throughput ≈ refill rate.

~/build

How the Rust version gets built

  1. 01Proxy core — hyper server + client with keep-alive pools; streaming bodies.
  2. 02Balancing — Pluggable strategies behind one function, health state shared via arc-swap.
  3. 03Resilience — Breakers, retry budgets, timeouts, outlier detection.
  4. 04Edge — rustls TLS termination with SNI; token-bucket limiter per client.
  5. 05Ops — Prometheus metrics, hot-reloadable config, graceful shutdown.

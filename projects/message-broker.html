~/overview

What it is, simply

A post office for events: producers drop messages into named topics, consumers read them at their own pace, and nothing is lost if a server dies.

Decoupling services through a durable log lets them scale, fail and replay independently.

PartitionsReplication & ISRHigh watermarkacksConsumer groupsRebalancingDelivery semantics

used in the real world

  • ›Apache Kafka, Redpanda, WarpStream
  • ›Event sourcing, CDC pipelines, stream processing (Flink, Kafka Streams)
  • ›Log aggregation and metrics pipelines

alternatives

  • ›Queue brokers (RabbitMQ, SQS) — per-message acks, no replay
  • ›Pulsar (compute/storage split)
  • ›NATS JetStream

limitations

  • !Ordering is per partition only
  • !acks=1 can lose acknowledged data on failover
  • !Exactly-once needs idempotent producers + transactions (not in mini)

~/internals

Learn the internals

01 High watermark

The line below which every in-sync copy has the data.

HW = min(LEO) over the ISR. Consumers read only below it, so they never see a record that could disappear on failover. acks=all completes when HW passes the record.

common mistake · Letting consumers read up to the leader's log end — they'd see records later truncated.

02 ISR

The list of followers that are keeping up.

A follower that hasn't caught up within replica.lag ticks is removed; it rejoins when caught up. Only ISR members may become leader (unless unclean election is enabled).

common mistake · min.insync.replicas = 1 with acks=all: it silently degrades to acks=1.

03 Consumer groups

Split the partitions among the consumers so each message is handled by one of them.

Each partition is owned by exactly one group member. Membership changes trigger a rebalance; members restart from committed offsets.

common mistake · More consumers than partitions: the extras sit idle.

04 Delivery semantics

Commit before work = may lose; commit after work = may duplicate.

At-most-once commits the offset first; a crash loses the rest of the batch. At-least-once processes first; a crash re-delivers. Exactly-once needs idempotence or transactions.

common mistake · Calling at-least-once 'exactly once' and not making handlers idempotent.

~/experiments

Guided experiments

Run these in the playground above. Write down what you expect before you start.

  1. E1 acks=1 vs acks=all

    objective ·
    See acknowledged data lost on failover.
    do ·
    Produce with acks=1, immediately kill the leader; repeat with acks=all.
    expect ·
    acks=1: durability audit lists lost acked records. acks=all: zero.

  2. E2 Slow follower

    objective ·
    Watch ISR shrink and expand.
    do ·
    Produce a burst with fetch batch 1.
    expect ·
    isr_shrink, then isr_expand after catching up.

  3. E3 Consumer crash

    objective ·
    Compare delivery semantics.
    do ·
    Crash a consumer mid-batch in each mode.
    expect ·
    At-least-once: duplicates, no loss. At-most-once: loss, no duplicates.

  4. E4 Rebalance

    objective ·
    Partition ownership changes.
    do ·
    Add and remove consumers.
    expect ·
    Generation increments; every partition owned exactly once.

~/build

How the Rust version gets built

  1. 01Log segments — Append-only segment files with sparse offset index and CRC per batch; mmap for reads.
  2. 02Replication — Follower fetch protocol, ISR management, leader epochs for safe truncation.
  3. 03Controller — Cluster metadata in a Raft quorum (reusing project 01's Raft).
  4. 04Group coordinator — Join/sync protocol, heartbeats, offset commits stored in an internal topic.
  5. 05Clients — Batching producer with retries + idempotence; consumer with poll loop.
